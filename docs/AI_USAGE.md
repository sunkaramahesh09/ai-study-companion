# AI Usage

*Submission requirement §20.5 — clearly distinguish **AI used to build the
product** from **AI used by the product**.*

These are two different things and the distinction matters, so they are kept in
two separate halves below. Nothing in Part A runs in production; everything in
Part B runs on every request.

---

## Part A — AI used to build the product

### What was used

| Tool | Model | What it did |
|---|---|---|
| **Claude Code** (CLI) | Claude Opus 5 | The primary development agent. Wrote the large majority of the application code, migrations, tests and documentation, working task-by-task from a plan it produced from the PRD |
| **Antigravity** | — | Generated a first-pass React UI on 2026-09-17, which was then reviewed and integrated by hand rather than adopted wholesale (see below) |

No other coding assistant, design tool or agent was used.

### How it was used

The full prompt record is in [`PROMPTS.md`](PROMPTS.md) — the actual prompts,
recovered from the session transcripts, not reconstructed. In summary:

- **One long opening prompt** fixed the stack, the two provider roles and their
  real rate limits, the engineering principles (deterministic learning core,
  validate structured output before persisting, isolation on every query) and
  the scope order, and asked for a **task list, not code**, as the first output.
- The build then ran task-by-task against that list. Most turns were a bare
  `continue`; the plan was the artifact, not the conversation.
- **Most corrections came from using the running app**, usually as a screenshot
  with a sentence. Six of the most consequential fixes in
  [`DECISIONS.md`](DECISIONS.md) — D-058 through D-061, D-073, D-074 — were
  found that way, by a person clicking through the product, not by the test
  suite.
- Every non-obvious choice was written to `DECISIONS.md` **as it was made**.
  That file is 77 numbered entries and is the honest audit trail of the
  collaboration, including the mistakes: a threshold documented as "measured"
  that never was (D-029), a web build that shipped a bundle with no application
  code in it and reported success (D-052), a data-isolation bug the tests could
  not have caught (D-073).

### What was *not* delegated

- **The engineering constraints.** The stack, the provider split, the rate-limit
  arithmetic, the deterministic-versus-generated boundary and the scope order
  were specified by the author up front, not proposed by the model.
- **Product judgement.** The navigation model, what belongs on which page, and
  what counts as a good answer were decided by the author from using the app —
  including the two most recent changes, the Tutor's progress answers (D-075)
  and where AI activity belongs (D-077).
- **Verification.** Claims were checked against the deployed system, not
  accepted from the model: the production rehearsal, the live evaluation suite
  and the browser passes all exist because "it should work" is not evidence.

### Honesty about the externally-generated UI

On 2026-09-17 a React UI generated by Antigravity was brought in. The
instruction was explicit that the existing backend must be preserved and the UI
integrated *only if it could be done safely*. It was reviewed, taken apart and
integrated piece by piece against the existing API and auth, not dropped in.
Several of its assumptions did not survive — for example it assumed emoji icons,
which were replaced with a line-icon set.

### Attribution in the repository

Commits made with the agent carry a `Co-Authored-By: Claude` trailer, so the
collaboration is visible in `git log` rather than implied. `CLAUDE.md` at the
repository root is the standing instruction file the agent read at the start of
every session — it is a development artifact, not application configuration.

## Part B — AI used **by** the product

### Providers and models

Two providers with two distinct roles, behind one interface in
[`packages/ai`](../packages/ai) so either can be replaced without touching the
application.

| Role | Provider | Model | Why |
|---|---|---|---|
| **Generation** — primary | Groq (OpenAI-compatible endpoint, `openai` SDK with a `baseURL` override) | `openai/gpt-oss-120b` | Grounded Tutor explanations, where reasoning quality is worth the token cost |
| **Generation** — fallback | Groq | `openai/gpt-oss-20b` | Short, high-volume work. **A separate quota pool**, so grading and question wording cannot starve the Tutor |
| **Embeddings** | Google Gemini | `gemini-embedding-001`, 768 dimensions | RAG indexing and query-side retrieval. Free tier, batched ~20 and paced ~700 ms apart |

Failover is automatic primary → fallback on a 429 that backoff could not clear.
Both providers retry with exponential backoff plus full jitter.

**The binding constraint is TPM, not RPM** — 8,000 tokens per minute per model.
That single fact shaped retrieval size (6 chunks, 1,600 token cap), prompt
length, history depth (4 turns) and the decision to keep refusals
model-free. See D-016, D-022, D-062.

### Where the product calls a model — and where it deliberately does not

| Feature | Tier | What the model produces | What it does **not** decide |
|---|---|---|---|
| **Tutor answer** (`tutor_answer`) | primary | The explanation, grounded in retrieved chunks, with `[S#]` citations | Whether there is enough evidence to answer at all — that is a deterministic relevance gate |
| **Tutor progress answer** (`tutor_answer`) | fallback | The *wording* of a progress report | Where the learner stands or what to do next — computed by `buildStudyBrief` (D-075) |
| **Concept extraction** (`concept_extraction`) | primary | Concept names and one-line descriptions from a sampled subset of a document | — |
| **Question generation** (`question_generation`) | fallback | The wording of one question, its options and expected points | Which concept, which difficulty, which type — chosen by `selectNextQuestion` |
| **Open-answer grading** (`open_answer_grading`) | fallback | A score, what the learner understood, and what was missing | How that score moves mastery — `updateMastery` does that |
| **Recommendation** (`recommendation`) | fallback | Two or three sentences addressed to the learner | Whether to recommend anything, and about what — `evaluateTriggers` decides |

Everything in the right-hand column lives in
[`packages/shared/src/learning/`](../packages/shared/src/learning) as **pure
functions with no AI, no I/O and no clock except one passed in**. That is a
stated PRD evaluation criterion (§9, §10, §13) and it is why those behaviours are
testable without a provider, reproducible, explainable to the learner, and free
to run.

### Guarantees applied to every model call

- **Structured output is validated, never trusted.** Groq's JSON mode is not
  schema-locked. `generateJson()` requests JSON, puts the schema in the prompt,
  and then validates the parsed value against the real zod schema **before it is
  returned** — one repair attempt, then hard failure. Nothing unvalidated
  reaches the database or changes application state (PRD §8).
- **Material and user messages are data, never instructions.** Retrieved
  material appears only inside numbered `<source>` blocks, the learner's own
  question inside `<question>`, delimiters occurring in either are neutralised,
  and an output-side check catches the case where the model complied anyway
  (D-035, D-037).
- **Every call is recorded.** One row in `ai_requests` per call — feature,
  model, tier, status, latency, prompt/completion/total tokens, estimated cost,
  attempt count, error. No exceptions; the recorder is inside the provider.
- **A Tutor answer is never cached.** Only genuinely reusable generations are —
  a question for a given concept and difficulty, in `question_bank`. Returning a
  stored answer to a learner's own free-text question would be a correctness
  bug, not a performance win.

### AI evaluation

18 automated cases across five suites (`tutor`, `retrieval`, `assessment`,
`recommendation`, `security`), run against **real models** with
`npm run eval`. Grading is rule-based against a fixture document with a known
page layout rather than model-based — a model judging another model's citation
would be both more expensive and less trustworthy than checking whether the
cited page is the page the fact is printed on. See the Evaluation section of the
[README](../README.md).
